# Anvia Full-Stack Applications

> Current stable v1 implementation context for server streaming, React chat, durable chat, and messaging channels. Updated 2026-11-28; reviewed against Anvia SDK source 386b66ba and Channels source bc762e9.

Keep agents, provider credentials, tools, memory, retrieval, observers, continuations, and access
control on the server. Send only the reviewed Client Protocol to the browser.

```text
@anvia/react primitives or app components
        ↓ @anvia/react controller
@anvia/client HTTP transport
        ↓ ClientStreamRequest over JSONL or SSE
authenticated server route
        ↓ @anvia/client event projection
server-side Agent stream
        ↓ @anvia/server Response
```

## Packages

```sh
pnpm add @anvia/core @anvia/client @anvia/server
pnpm add @anvia/react react react-dom
```

- `@anvia/client` defines browser-safe request, event, message, and transport contracts.
  Subpaths: `@anvia/client/durable` (`DurableClient`, `DurableHttpError`) and
  `@anvia/client/durable-chat` (`createDurableChatTransport`, `DurableBusyError`).
- `@anvia/server` frames client events as a Fetch `Response` using JSONL or SSE;
  `@anvia/server/durable` exports `createDurableHandler()`.
- `@anvia/react` owns chat and completion controllers, cancellation, resumption, and interactions.
- `@anvia/react` primitives are headless and the package ships no CSS. The one exception is the
  sandbox terminal: import `@xterm/xterm/css/xterm.css` once when you render it.
- `@anvia/cli` can copy editable shadcn/Tailwind components into the application.

## Server route

The route is framework-independent because it uses standard `Request`, `Response`, and Web Streams.
Authenticate, rate-limit, and authorize before starting model work. `supportAgent` is the
application's server-side `Agent`.

```ts
import { agentToClientStream, parseClientStreamRequest } from '@anvia/client'
import { createClientStreamResponse } from '@anvia/server'
import { supportAgent } from './support-agent'

export async function POST(request: Request) {
  const body = parseClientStreamRequest(await request.json())
  if (body.type !== 'messages') {
    return new Response('Interaction responses are not enabled', { status: 400 })
  }

  return createClientStreamResponse({
    events: agentToClientStream({
      events: supportAgent.stream({ messages: body.messages }),
      ...(body.metadata === undefined ? {} : { metadata: body.metadata }),
    }),
    format: 'jsonl',
  })
}
```

Do not serialize raw runtime events directly. Projection is the security and compatibility boundary
where private errors, reasoning, provider payloads, tool inputs, and tool outputs are omitted or
mapped to intentional public events.

Return the stream with `createClientStreamResponse()`. `createHttpClientTransport()` rejects any
response without the `x-anvia-stream-protocol: anvia.client.v3` header, so a hand-rolled response
fails on the client.

## React controller

```tsx
import { createHttpClientTransport } from '@anvia/client'
import { useChat } from '@anvia/react'
import { useState } from 'react'

const transport = createHttpClientTransport({ endpoint: '/api/chat', format: 'jsonl' })

export function Chat() {
  const chat = useChat({ transport })
  const [input, setInput] = useState('')
  const busy = chat.status === 'submitted' || chat.status === 'streaming' || chat.status === 'waiting'

  return (
    <form onSubmit={(event) => {
      event.preventDefault()
      void chat.sendMessage({ text: input })
      setInput('')
    }}>
      {chat.messages.map((message) => (
        <div key={message.id}>
          {message.parts.map((part) => part.type === 'text' ? part.text : null)}
        </div>
      ))}
      <input value={input} onChange={(event) => setInput(event.target.value)} />
      <button disabled={busy}>Send</button>
      <button type="button" onClick={chat.stop}>Stop</button>
    </form>
  )
}
```

`chat.status` is `ready`, `submitted`, `streaming`, `waiting`, or `error`. `waiting` means the stream
ended suspended on a pending approval or question: answer it with `respondToInteraction()` instead
of sending a new message.

The server defaults to JSONL. The client transport defaults to `auto` and infers the format from the
response `content-type`; set the same explicit `format` at both ends when a proxy may rewrite
headers. Use SSE when existing infrastructure requires it. Test proxy buffering, idle timeouts,
disconnect cancellation, and maximum request duration in the deployed environment.

## Headless UI or editable components

Use the CLI when the application wants an editable starting point:

```sh
pnpm dlx @anvia/cli ui init
pnpm dlx @anvia/cli ui add chat
```

Or compose headless primitives directly:

```tsx
import { ChatProvider, ComposerPrimitive, MessagePrimitive, ThreadPrimitive } from '@anvia/react'

export function ChatView({ chat }) {
  return (
    <ChatProvider controller={chat}>
      <ThreadPrimitive.Root className="chat-thread">
        <ThreadPrimitive.Viewport>
          <ThreadPrimitive.Messages>
            <MessagePrimitive.Root className="chat-message">
              <MessagePrimitive.Content>
                <MessagePrimitive.Parts />
              </MessagePrimitive.Content>
            </MessagePrimitive.Root>
          </ThreadPrimitive.Messages>
        </ThreadPrimitive.Viewport>
        <ComposerPrimitive.Root className="chat-composer">
          <ComposerPrimitive.Input placeholder="Send a message..." />
          <ComposerPrimitive.Stop>Stop</ComposerPrimitive.Stop>
          <ComposerPrimitive.Submit>Send</ComposerPrimitive.Submit>
        </ComposerPrimitive.Root>
      </ThreadPrimitive.Root>
    </ChatProvider>
  )
}
```

`ChatProvider` also accepts `transport` and other `useChat` options instead of `controller`, and
creates the chat itself; read it with `useChatContext()`.

There is no package stylesheet and no `data-anvia-*` styling contract. Use application classes,
`asChild`, ARIA, `data-state`, and `data-role`. CLI output belongs to the application and can be
edited freely; the `@anvia/react` primitives remain the behavior and accessibility foundation.

## Interactions

Client Protocol v3 represents approval and question responses as `interaction_response` requests.
In React, read `chat.interactions.pending` (each entry carries the full request under `request`) and
answer with:

```ts
await chat.respondToInteraction({
  interactionId,
  response: { type: 'tool-approval', approved: true },
})
// Questions: { type: 'tool-question', answers: [{ questionId, value }] }
```

`HumanInputPrimitive` renders pending interactions; `useApproval()` and `useQuestion()` read its
item context and must be used inside `HumanInputPrimitive.Approval` or `.Question`. These buttons do
not decide who may answer. The server must map the public interaction ID to a protected continuation
and verify actor, tenant, expiry, response type, and claim state. Side-effecting tools must remain
idempotent because retries and reconnects cannot create an exactly-once guarantee.

## Resumption

```ts
const chat = useChat({
  transport,
  resume: { key: 'support-chat', storage: 'sessionStorage', auto: true },
})
```

The hook stores the stream ID, latest event ID, messages, interactions, and last request, and clears
them when the stream ends. Resuming needs a matching server route: pass
`resumable: { streamId, store }` to `createClientStreamResponse()`, and when the request carries
`body.resume`, authorize it and replay with `resumeClientStreamResponse({ streamId, after, store })`.
`createMemoryResumableStreamStore()` is process-local and loses records on restart.
Use durable shared storage across replicas, authorize both thread and stream ownership, and apply
retention/deletion policy separately to messages, uploads, stream envelopes, memory, and telemetry.

## Cancellation

`chat.stop()` aborts the request. For a normal `createClientStreamResponse()` route, cancelling the
response body calls `return()` on the event iterator, and closing an active `AgentStream` cancels its
run; server code can also call `stream.cancel(reason)`. A resumable stream deliberately keeps
draining and storing the run after the reader disconnects. Cancellation never undoes completed tool
calls or external writes. Platforms and proxies may still terminate work after a disconnect.

## Authentication

Authenticate and authorize in the route before any model or tool call, and make authentication
failures cost zero provider calls. Browser history is untrusted content, not identity. For durable
backends, `createDurableHandler({ runtime, authorize })` calls `authorize(request, resource)` for
every operation, including reads; return `false` to deny. Trace context comes only from the server's
`trace(request, resource)` hook. `DurableClient` sends application credentials through its
`headers` (static or async function) and `credentials` options.

## Durable chat

When the backend is a `@anvia/durable` endpoint served by `createDurableHandler()`, create a
`DurableClient({ endpoint })` and one
`createDurableChatTransport({ client, agentId, sessionId })` per chat session, then pass the
transport to `useChat`, or use `useDurableChat()` to get the chat plus run identity, status, and
controls (`steer`, `cancel`, `retry`, `resolveTool`, `resolveMemoryWrite`).

The adapter submits only the last user message, maps durable journal events to Client Protocol
frames, routes interactions to the active run, and uses the durable run ID and sequence as the
resume cursor. `chat.stop()` detaches the subscription; it does not cancel the run. Use
`transport.controller.cancel()`, `retry()`, or `reattach()` explicitly.

A busy session (HTTP 409) surfaces as `DurableBusyError`. Its `runId` is the unfinished run when it
could be read back and `undefined` otherwise; reattach to it instead of submitting again.

Payload limits (`maxPayloadBytes`) apply at two points:

- A prompt over the limit is rejected at submission: the handler returns 413 with
  `code: 'payload_too_large'` and `field: 'run.prompt'`, and no run is created.
- Inherited session history or input that exceeds the limit when the run starts ends that run in
  terminal `failed`; it never parks in `needs_attention` and is never retried with truncated history.

The handler's `maxBodyBytes` (default 64 KiB) is the binding ceiling for request bodies and uploads;
capacity limits return 429 with `Retry-After`.

## Production checklist

- Validate actual request bytes, message/part counts, text lengths, metadata, and attachments.
- Treat browser history as untrusted content, not identity or system instruction.
- Enforce same-origin or narrow credentialed CORS and HTTPS.
- Ensure authentication failures cause zero provider and tool calls.
- Sanitize public errors and keep credentials and observability payloads server-side.
- Test aborts, reconnects, duplicate interaction decisions, cross-tenant IDs, and proxy buffering.

## Messaging channels

Anvia Channels (`@anvia/channel`, `@anvia/channel-agent`, `@anvia/discord`, `@anvia/slack`,
`@anvia/telegram`) is a separate pre-1.0 workspace for Node.js 24+. `@anvia/channel-agent` declares
`@anvia/core` `^1.21.0` as a peer.

```ts
import { createChannelAgent } from '@anvia/channel-agent'
import { telegram } from '@anvia/telegram'

// `agent` is the application's existing @anvia/core Agent.
const service = createChannelAgent({
  channel: telegram({ token: process.env.TELEGRAM_BOT_TOKEN! }),
  agent,
  streaming: { placeholder: 'Thinking…' },
})

await service.start()
process.once('SIGTERM', () => void service.stop())
```

- Default filtering accepts direct messages and mentions from non-bot senders.
- Per-sender sessions apply only when the agent has a memory store.
- Slash commands (`commands`) and acknowledgement reactions (`acknowledge`) are opt-in. Commands skip
  the top-level `shouldHandle`; authorize them with `commands.shouldHandle`.
- For proactive sends, `sendChannelMessage()` from `@anvia/channel` splits text at the platform limit
  and puts actions and attachments on the final part. Wrap an adapter with
  `createRateLimitedChannel()` (also `@anvia/channel`) for pacing.
- The application owns bot credentials, user authorization, interaction persistence, and deployment.
