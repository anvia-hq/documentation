# Anvia Evaluations and Observability

> Current stable v1 context for tracing, runtime scoring, evaluation suites, datasets, and release gates. Lens guidance reviewed 2026-11-23 against server v0.20.0; SDK review remains at the compatibility inventory baseline.

Use unit and integration tests for deterministic code. Use evaluations for model behavior whose
wording or reasoning can vary. Observability explains runtime activity; it is not application state.

```text
instrument runtime → inspect traces → curate failures into cases
→ run versioned suites → compare candidates → enforce a release gate
```

## Trace with Lens

```sh
pnpm add @anvia/core @anvia/lens
```

```ts
import { Agent } from '@anvia/core'
import { LensClient } from '@anvia/lens'

const lens = new LensClient()
const agentTracing = lens.observer({ captureMode: 'safe' })
const pipelineTracing = lens.pipelineObserver({ captureMode: 'safe' })

const agent = new Agent({
  id: 'support',
  model,
  observability: {
    observers: { lens: agentTracing },
    primaryTrace: 'lens',
  },
})
```

Configure `pipelineTracing` in a Pipeline constructor under the same `lens` observer name and select
`primaryTrace: 'lens'`. Core then parents the Agent run beneath its Pipeline stage, so Lens stores one
trace containing orchestration, model generation, and tool spans. Different primary names remain
separate traces.

`LensClient` reads server-only `ANVIA_LENS_*` credentials. Use `{ optional: true }` only when a
missing complete connection should disable telemetry; partial credentials still fail fast. Call
`flush()` before short-lived processes exit and `close()` during graceful shutdown. On a process
signal, stop accepting work, abort and await active Agent and Pipeline runs, then close Lens so
cancelled root observations can finish before the provider flushes.

Use stable opaque user, session, trace, release, and environment identifiers. Review capture mode,
redaction, retention, and region before sending prompt, response, tool, retrieval, or metadata
payloads. Lens telemetry must not replace conversation memory, product records, or audit logs.

## Record runtime feedback

Use runtime scoring when feedback or a production check should be observable without running an
evaluation suite:

```ts
await lens.score({
  id: feedbackId,
  traceId,
  observationId,
  name: 'user-feedback',
  value: liked ? 1 : 0,
  dataType: 'BOOLEAN',
  source: 'end_user',
  comment,
  metadata: { channel: 'thumbs' },
})
```

Boolean scores use `1` or `0`; numeric and categorical scores are also supported. Use a stable
opaque score ID when later feedback should replace or supersede the same application record. A
valid trace ID is required, comments are limited to 2,000 characters, and application code owns
authentication, authorization, metadata validation, and delivery boundaries. Call `flush()` or
`close()` when queued Lens logs must be delivered.

## Run an evaluation suite

Fragments below use application-owned identifiers: `model`, `judgeModel`, `agent`, `suite`, `myTarget`, `cases`,
`metrics`, `traceId`, `observationId`, `feedbackId`, `liked`, and `comment` come from your code.

```ts
import { agentEvalTarget, contains, createJudgeMetrics, notBlank, runEvalSuite } from '@anvia/core/evals'

const judge = createJudgeMetrics({ model: judgeModel, includeReason: 'on-fail' })

const result = await runEvalSuite({
  name: 'support-policy-v3',
  cases: [
    { id: 'refund-window', input: 'When can I request a refund?', expected: '30 days' },
    { id: 'billing-owner', input: 'Who changes billing?', expected: 'Workspace owners' },
  ],
  target: agentEvalTarget(agent),
  metrics: [
    notBlank(),
    contains({ caseSensitive: false }),
    judge.llmScore({ name: 'answers_directly', threshold: 0.75, criteria: 'Answers the question directly.' }),
  ],
  concurrency: 2,
})

console.log(result.passed, result.results[0]?.scores.contains)
```

`scores` and `metricSummaries` are keyed by metric `name`, whose defaults are snake_case
(`exact_match`, `not_blank`, `contains`); pass `name` for a readable or unique key.

## Repeat, cache, and gate

`agentEvalTarget(agent)` adapts a string-prompt agent directly; the options form is required only
when a case input is not a string. `trials` repeats a case and `minPassRate` decides how many
samples must pass, `tags` selects cases, and `targetCache` or `cachedEvalTarget` reuses target
outputs. `result.passed` is the gate; `result.metricSummaries` reports per-metric `passRate`.

```ts
import {
  assertEvalPassed, cachedEvalTarget, compareEvalResults, createMemoryEvalCache,
  loadEvalResult, runEvalCli, runEvalSuite, saveEvalResult,
} from '@anvia/core/evals'

const target = cachedEvalTarget(myTarget, createMemoryEvalCache())
const run = await runEvalSuite({ ...suite, target, trials: { count: 3, minPassRate: 2 / 3 }, tags: ['smoke'] })
assertEvalPassed(run)

await saveEvalResult('evals/baseline.json', run)
const baseline = await loadEvalResult('evals/baseline.json')
const comparison = compareEvalResults(baseline, run, { scoreTolerance: 0.02 })

await runEvalCli({
  ...suite,
  argv: true,
  exitCode: true,
  baselinePath: 'evals/baseline.json',
  savePath: 'evals/baseline.json',
})

console.log(comparison.hasRegressions)
```

Flags are read only with `argv: true` (or an explicit array). `evalExitCode` returns `2` for a
required invalid judgment, `1` for a required failure, and `0` otherwise; `exitCode: true` raises
`process.exitCode` and never lowers it; `failOnRegression: false` reports baseline regressions
without raising it. Without a `scoreTolerance`, same-outcome score drift is
`unchanged`, and optional-metric regressions do not gate unless `includeOptionalMetrics` is set.

Agent trajectories have their own metrics: `toolCalled`, `toolNotCalled`, `toolCallOrder`,
`maxTurns`, `maxTokens`, and `maxDurationMs`. `createJudgeMetrics({ model })` shares one judge
model and defaults across the judge metrics.

Since `@anvia/core` 1.24.1, judges omit `temperature` unless set; `temperature` is opt-in on
`llmJudge`, `llmScore`, the task-specific judges, and `createJudgeMetrics`. Anthropic models declare
`temperature: false` and reject it with `CompletionCapabilityError`, so leave it unset for them.

Start with deterministic checks. Add semantic similarity, judge, score, RAG, or conversation metrics
only when each one represents a named product requirement. Judge metrics add cost and variance.

Each case can pass, fail, or be invalid. Invalid means the target or metric could not make a valid
judgment; never silently count it as passing. An invalid outcome's `kind` is `target`, `metric`,
`configuration`, `provider`, or `timeout`; `EvalOutcome.fromError()` infers it from the error chain
(provider SDK errors and HTTP 4xx/5xx are `provider`) and appends the cause message to the reason. Include negative controls that must fail so a broken evaluator
cannot make every candidate look good.

## Report suites and use managed datasets

```ts
import { agentEvalTarget, runEvalSuite } from '@anvia/core/evals'
import { LensClient } from '@anvia/lens'

const lens = new LensClient({ serviceName: 'support-evals' })
const reporter = lens.evalReporter({ includeMetadata: true, includePayloads: false })

try {
  await runEvalSuite({
    name: 'support-regression',
    cases,
    target: agentEvalTarget<string>({
      agent,
      request: ({ input }) => ({ prompt: input }),
    }),
    metrics,
    reporters: [reporter],
  })
  await lens.flush()
} finally {
  await lens.close()
}
```

Use an observer from the same client as the reporter, registered under `lens`, and select
`primaryTrace: 'lens'`. Custom names must match reporter `traceObserver`. Configure `onMissingTrace`
deliberately; `ignore`/`warn` omit uncorrelated results. Keep `publishInvalid: true` for evidence
budgets, which measure received judgments rather than attempted evaluations.

The public dataset client reads published immutable versions:

```ts
const datasets = lens.datasetClient()
const dataset = await datasets.getDataset<string, string>({
  name: 'support-cases',
  version: 'v2',
})
```

Dataset retrieval is capped at 100 pages: default 50/page supports 5,000 cases; 100/page supports
10,000. Exceeding it throws `pagination_limit`. Run-detail case summaries/search/outcome filters
cover the current 100-result page; header/metric totals cover the entire run.

Pin dataset, prompt, model, retrieval, runtime, and evaluator versions in CI. Drafting, publishing,
archiving, comparison, and quality-gate configuration live in Lens; the SDK client is read-only.

## Workspace and prompt operations

Lens members can access all projects in their workspace; projects separate telemetry/keys/retention,
not member-access groups. MCP tokens independently grant workspace-wide read-only diagnostics; raw
payloads need token permission plus an explicit includePayload request. Revoke exposed tokens
separately from membership removal and review OIDC provisioning eligibility during offboarding.

Lens prompt UI commits immutable numeric versions and moves labels to deploy or roll back. The
SDK reads/compiles templates; pass the resolved prompt.ref as trace.promptRef or run.promptRef.
Notifications support Slack, Discord, Telegram, and webhook on incident opening. System Health
provides owner/admin diagnostics for host capacity, rejected ingestion, worker heartbeats, and queues.

## Release gates

A completed suite is evidence, not a deployment decision. CI or the release system must define
required metrics, slices, minimum sample sizes, invalid-result policy, variance tolerance, and the
candidate/baseline comparison. A gate should return pass, fail, or insufficient data.

Use synthetic or approved data, separate tenant records, redact before external judges/reporters,
and track evaluator cost and latency. Manually review a sample of disagreements and repeat
model-judged cases to estimate variance.
